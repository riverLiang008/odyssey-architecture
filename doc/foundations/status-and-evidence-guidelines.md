# Odyssey 设计内容类型与来源标注规则

> Status: Approved  
> Task: ODOC-004  
> Language: Chinese source of truth  
> Updated: 2026-09-21

## 1. 目的

Odyssey 文档的任务不是汇报产品开发进度，而是解释这套 AI Agent 系统为什么这样设计。

本文只解决一个问题：当正文同时使用当前 Figma、早期设计图、概念图和未来方向时，怎样让读者知道每段内容在设计论证中扮演什么角色，而不会把历史方案、探索方向或示意图误认为当前设计。

它不建立工程完成度体系，也不要求作者逐项说明功能是否已经开发完成。

## 2. 文档关注什么

每篇正文应优先回答：

1. 我们观察到了什么问题；
2. 为什么常见表达或已有方案不足；
3. Odyssey 做出了什么设计选择；
4. 为什么做出这个选择；
5. 这个选择带来了什么收益、限制和代价；
6. 设计从早期方案演化到今天时，哪些认识发生了变化。

正文不以功能清单、开发里程碑、测试覆盖率或交付状态为主线。

## 3. 四种设计内容类型

### 3.1 `Current Design` / 当前设计

Odyssey 当前采用、并可作为本轮设计论证依据的设计方向。

主要来源包括当前 Figma、River 已确认的设计决定，以及与当前 Figma 一致的产品或领域说明。写作时应说明它解决的具体问题，只描述来源能够支持的交互、结构或语义，避免从界面外观推断未表达的系统行为。

`Current Design` 表示当前设计主张，不表示对应能力已经开发完成。

### 3.2 `Exploration` / 设计探索

正在考虑、但尚未成为当前设计结论的方向。适用于存在多个候选方案，或者关键语义、交互和边界仍未决定的内容。

探索内容必须写出尚未决定的问题，不使用承诺式语言，也不能让高完成度的视觉稿掩盖其未决性质。

### 3.3 `Historical Design` / 历史设计

Odyssey 曾经采用或认真考虑过、如今主要用于解释设计演化的方案。主要来源包括旧飞书文档、早期 Figma 页面和已经被当前设计取代的概念模型。

历史材料的价值不是证明“以前做错了”，而是呈现：

- 当时试图解决什么问题；
- 方案暴露了什么不足；
- 哪个新认识推动了变化；
- 当前设计保留、改变或放弃了什么。

历史图必须带有时间或版本说明，并解释它与当前设计的关系。

### 3.4 `Deferred` / 已后置

团队已经明确决定不在当前文档版本中展开的设计主题或案例。

`Deferred` 必须来自明确的范围决定，并说明它为何不阻塞当前论证。“尚未找到材料”“还没核验”或“暂时不知道怎么写”都不等于 `Deferred`。

当前 Research Assistant 案例属于这一类：案例设计尚未开始，并已明确后置到独立 Epic，因此首版不应为了叙事完整而虚构案例流程。

## 4. 图像来源的职责

| 图像类型 | 在文档中的职责 | 必须说明 |
| --- | --- | --- |
| 简化概念图 | 解释一个设计关系或核心矛盾 | 这是概念表达，不是产品界面 |
| 当前 Figma 裁切图 | 展示当前设计如何落到界面与交互 | Figma 节点、裁切范围、必要标注 |
| 历史图 | 解释早期假设与设计演化 | 时间或版本、已被什么取代 |
| 探索图 | 展示尚未决定的方向 | 未决问题、不得视为当前设计 |
| 对照图 | 比较旧方案与当前方案 | 比较维度、变化原因 |

一张图只承担一种主要责任。需要同时讲历史与当前设计时，优先并置两张图，而不是让读者从一张未标注的旧图中猜测。

## 5. 最小来源记录

设计文档不是研究论文，不需要为每句话堆叠证据；但关键设计结论必须能回到其来源。

推荐在页面底部维护简洁的“设计来源”区：

```md
## 设计来源

- 当前设计：Figma，`[页面 / 节点名称]`，核对日期 YYYY-MM-DD
- 历史设计：`[文档或图片路径]`，约 YYYY-MM
- 设计确认：River，YYYY-MM-DD
```

来源记录要证明的是“这确实是当前或历史设计”，而不是“产品已经实现”。

## 6. 页面与局部标注方式

大多数正式页面默认讲当前设计，无需在每一段重复贴标签。页面开头可以写：

```md
> 本页解释 Odyssey 当前采用的设计方向。界面依据当前 Figma；历史材料会单独标注。
```

历史片段：

```md
> **设计原则图**  
> 这张图说明 Odyssey 一直采用的三色 Thinking Ownership。它是概念表达；具体界面形态以当前 Figma 为准。
```

探索片段：

```md
> **设计探索**  
> 以下方向尚未成为当前设计。仍需决定：[未决问题]。
```

后置主题：

```md
> **已后置**  
> 本主题不在首版范围内：[原因]。它不影响本页的核心设计结论。
```

标签用于防止误读，不应喧宾夺主。页面如果只有当前设计，就不需要制造状态面板或状态表格。

## 7. 什么时候提到开发状态

默认不提。

只有当页面中的画面很容易被理解为可操作产品、而这种误解会影响设计论证时，才使用一句局部说明：

> 这里展示的是当前交互设计，用于解释导航关系；本文不讨论其开发进度。

设计正文中不加入：

- `Implemented` / `In development` 徽标；
- 代码文件和测试作为常规引用；
- 功能完成百分比；
- 按开发状态组织的能力矩阵；
- 为证明产品可用而进行的逐项验收。

开发完成度应由工程文档、项目管理或发布说明承载。

## 8. 冲突处理

### Figma 与旧文档冲突

以 Figma 作为当前设计；旧文档只在设计演化中引用，并明确标注为历史材料。

### Figma 与当前文字规范冲突

如果差异只是名称，可按照已冻结术语统一表达；如果涉及对象含义、层级、控制边界或用户路径，暂停相关陈述并向 River 确认。

### 当前 Figma 内部不一致

不自行选择最像成品的一页。记录冲突节点和它影响的设计结论，向 River 确认哪一个代表当前方向。

### 设计与代码不一致

本套文档以解释设计为目标，因此仍以当前 Figma 表达设计意图。除非正文明确讨论“设计如何落地”，否则不需要让设计叙事迁就当前开发进度。

## 9. 中文与英文的一致性

中文是内容和设计判断的基准版本。英文版应保持相同的当前设计结论、内容类型、图像版本、限制、代价、未决问题和来源指向。

英文可以自然改写，但不能把“探索”翻译成已经采用的设计，也不能把“当前设计”扩展成产品能力承诺。

## 10. 应用到首版样章

《为什么是双层 Canvas》样章应：

- 以当前 Figma 解释 Journey Canvas 与 Agent Workflow Canvas 的职责分离；
- 用简化概念图解释为什么一个视图不足以同时承担旅程编排与 Agent 内部工作流设计；
- 只有在能解释设计变化时才加入旧图；
- 将三色 Thinking Ownership 图标为设计原则图，并说明同一原则如何同时体现在区域、节点、变量分组与资源边界中；
- 只把未确定的交互作为设计探索呈现；
- 不调查或罗列对应界面是否已经开发完成；
- 继续后置 Research Assistant 案例，不为样章虚构端到端流程。

## 11. Review 检查表

- [ ] 页面主线是在解释设计问题与选择，而不是介绍功能；
- [ ] 当前设计以 Figma 或 River 确认为依据；
- [ ] 历史图有时间、版本和演化说明；
- [ ] 探索内容明确写出尚未决定的问题；
- [ ] 后置内容来自明确范围决定；
- [ ] 概念图没有被伪装成产品界面；
- [ ] 当前 Figma 截图没有被写成产品已经可用的证明；
- [ ] 设计收益同时呈现了限制或代价；
- [ ] 不必要的开发状态、代码路径和测试信息已从正文移除；
- [ ] 中英文内容类型和来源保持一致。

## 12. ODOC-004 完成边界

ODOC-004 完成表示首版已经有统一的设计内容分类和来源标注方式。它不要求对 Odyssey 当前开发状态进行审计。

后续页面只需要准确区分当前设计、设计探索、历史设计和已后置内容，并围绕“为什么这样设计”展开论证。

## 13. River Review 结论

River 于 2026-09-21 确认：

1. 正文默认只讲当前设计，不显示开发状态；
2. 使用 `Current Design`、`Exploration`、`Historical Design`、`Deferred` 四种内容类型；
3. 仅在 Figma 画面可能造成严重误解时，局部说明“本文不讨论开发进度”；
4. 不再安排独立的当前实现状态核验任务。
